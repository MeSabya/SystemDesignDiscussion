# Go Concurrency: Singleflight with gRPC

## 1. What is Singleflight?

`golang.org/x/sync/singleflight` is a Go concurrency utility that prevents multiple goroutines from executing the same expensive operation simultaneously.

It implements **in-flight request deduplication**.

When multiple goroutines request the same operation using the same key:

- The first goroutine executes the operation.
- Other goroutines wait for the first execution to complete.
- The result or error is shared with all waiting goroutines.
- Requests with different keys execute independently.

**Important:** Singleflight does not cache results. It only deduplicates concurrent executions.

---

## 2. Problem Statement: Duplicate Concurrent Operations

Consider a Go-based gRPC service exposing an API to retrieve Kubernetes cluster metadata.

```protobuf
service ClusterService {
    rpc GetCluster(GetClusterRequest) returns (GetClusterResponse);
}
```

The service fetches cluster metadata from the Kubernetes API server.

### Scenario

Assume:

- 100 clients send concurrent RPC requests.
- All requests are for `cluster-101`.
- The cluster metadata is not cached.
- A Kubernetes API lookup takes approximately 2 seconds.

### Without Singleflight

Each incoming RPC is handled independently by the gRPC server.

All 100 handlers execute the same downstream lookup.

```text
                100 RPC Requests
                       |
                       v
                 gRPC Server
                       |
             100 Handler Goroutines
                       |
          +------------+------------+
          |            |            |
          v            v            v
       Lookup 1     Lookup 2     Lookup 3
          |            |            |
          +------------+------------+
                       |
                       v
              Kubernetes API Server
```

Potential consequences:

- Duplicate Kubernetes API calls.
- Increased API-server load.
- Increased database or downstream service connections.
- Unnecessary CPU and network consumption.
- Increased probability of rate limiting.
- Potential cascading failures under heavy traffic.

This is a form of duplicate work and, in cache-miss scenarios, contributes to a **cache stampede (thundering herd)**.

### With Singleflight

All RPC handlers still execute concurrently, but duplicate downstream operations are suppressed.

```text
                 100 RPC Requests
                        |
                        v
                  gRPC Server
                        |
              100 Handler Goroutines
                        |
                        v
                 Singleflight Group
                        |
                 Key: cluster-101
                        |
             +----------+----------+
             |                     |
             v                     v
        Leader Goroutine      Duplicate Callers
             |                     |
             v                     v
       Kubernetes API           Wait()
             |
             v
       Cluster Metadata
             |
             +---------------------+
                        |
                        v
               Shared Result
                        |
                        v
               100 RPC Responses
```

Expected outcome:

| Metric | Without Singleflight | With Singleflight |
|---|---:|---:|
| Incoming RPC calls | 100 | 100 |
| Handler invocations | 100 | 100 |
| Downstream lookups | 100 | 1 |
| Results returned | 100 | 100 |

The actual deduplication happens only when calls overlap in time.

## 3. How Singleflight Works Internally

The `singleflight.Group` maintains an internal map of currently executing operations.

Conceptually:

```go
type Group struct {
    mu sync.Mutex
    m  map[string]*call
}

type call struct {
    wg   sync.WaitGroup
    val  any
    err  error
    dups int
}
```

### Execution flow

**Step 1: First request arrives**

- Acquires the group mutex.
- Checks whether the key exists.
- Key is absent.
- Creates a new call entry.
- Stores the entry in the map.
- Releases the mutex.
- Executes the actual function.

This goroutine becomes the leader.

**Step 2: Duplicate request arrives**

- Acquires the group mutex.
- Finds an existing call for the same key.
- Increments the duplicate count.
- Releases the mutex.
- Waits on the existing call's WaitGroup.

**Step 3: Original operation completes**

- Stores the result and error.
- Removes the key from the in-flight map.
- Signals completion using WaitGroup.Done().

**Step 4: Waiting goroutines resume**

- All waiting goroutines receive the same result or error.
- They do not execute the underlying function again.

### Important implementation detail

The global mutex is not held while the expensive operation executes.

It protects only the in-flight map and coordination state.

Therefore, different keys can execute independently.

For example:

```text
cluster-101 --> One execution
cluster-101 --> Wait
cluster-101 --> Wait

cluster-202 --> Independent execution
cluster-202 --> Wait
```

## 4. Singleflight API

The package exposes three important methods.

### 4.1 Do()

```go
result, err, shared := group.Do(
    "cluster-101",
    func() (any, error) {
        return fetchClusterMetadata("cluster-101")
    },
)
```

- Executes the function if no matching operation is running.
- Otherwise waits for the existing operation.
- Returns the result, error and shared indicator.

`shared` indicates whether the result was shared with multiple callers.

### 4.2 DoChan()

```go
resultCh := group.DoChan(
    "cluster-101",
    func() (any, error) {
        return fetchClusterMetadata("cluster-101")
    },
)

select {
case result := <-resultCh:
    fmt.Println(result.Val)

case <-ctx.Done():
    fmt.Println("Caller stopped waiting")
}
```

Useful when callers need independent cancellation of their wait.

Note: Cancelling the caller's wait does not automatically cancel the shared operation.

### 4.3 Forget()

```go
group.Forget("cluster-101")
```

Removes the key from in-flight tracking.

A subsequent caller can start a new execution even if the original execution is still running.

Use carefully because this can allow duplicate concurrent operations for the same key.

## 5. Implementation Architecture: gRPC + Singleflight

### Project structure

```text
grpc-singleflight/
│
├── proto/
│   └── cluster.proto
│
├── gen/
│   └── cluster/
│       ├── cluster.pb.go
│       └── cluster_grpc.pb.go
│
├── cmd/
│   ├── server/
│   │   └── main.go
│   └── client/
│       └── main.go
│
├── internal/
│   ├── service/
│   │   └── cluster.go
│   └── repository/
│       └── cluster.go
│
└── go.mod
```

### Responsibility separation

| Component | Responsibility |
|---|---|
| Proto | Defines RPC contract |
| Client | Sends concurrent RPC calls |
| Server | Starts gRPC server |
| Service | Handles RPC and applies singleflight |
| Repository | Fetches Kubernetes metadata |
| Singleflight Group | Deduplicates concurrent lookups |

### Service implementation

```go
type ClusterService struct {
    pb.UnimplementedClusterServiceServer

    repo  *repository.ClusterRepository
    group singleflight.Group
}

func (s *ClusterService) GetCluster(
    ctx context.Context,
    req *pb.GetClusterRequest,
) (*pb.GetClusterResponse, error) {

    clusterID := req.GetClusterId()

    result, err, shared := s.group.Do(
        clusterID,
        func() (any, error) {

            lookupCtx, cancel := context.WithTimeout(
                context.Background(),
                5*time.Second,
            )
            defer cancel()

            return s.repo.GetCluster(lookupCtx, clusterID)
        },
    )

    if err != nil {
        return nil, status.Errorf(
            codes.Internal,
            "failed to fetch cluster: %v",
            err,
        )
    }

    _ = shared

    return result.(*pb.GetClusterResponse), nil
}
```

**Why is Group part of the service struct?**

All RPC handler invocations must share the same Group instance.

If a new Group is created inside every `GetCluster()` invocation, requests cannot deduplicate one another.

The example uses a separate bounded context for the shared lookup so that cancellation of the first RPC caller does not automatically cancel the lookup for everyone.

Production implementations should also consider service shutdown, timeout policy, and whether the shared operation should continue when no callers remain.

## 6. Real-World Use Cases

Singleflight is useful whenever multiple concurrent callers request the same expensive operation.

### Use case 1: Cache stampede prevention

**Problem:**

A cache entry expires and 100 requests simultaneously encounter a cache miss.

Without singleflight, all 100 requests may query the database.

**Solution:**

```text
Request
   |
   v
Check Redis
   |
   +-- HIT --> Return cached data
   |
   +-- MISS
         |
         v
     Singleflight
         |
         v
     Database Query
         |
         v
     Update Redis
         |
         v
     Return Result
```

Only one database lookup happens for overlapping requests with the same key.

### Use case 2: Kubernetes API lookups

**Problem:**

Multiple controllers, RPC handlers or internal operations request the same Kubernetes resource metadata simultaneously.

For example:

```text
Namespace: production
Resource: PSMDB
Name: mongo-101
```

Repeated API-server lookups create unnecessary load.

**Solution:**

Use a composite key:

```go
key := namespace + "/" + resourceName
```

Deduplicate concurrent lookups for the same resource.

Note: This does not replace controller-runtime caches or Kubernetes informers. It is useful for additional expensive operations that are not already efficiently served by those caches.

### Use case 3: AWS token refresh

**Problem:**

Multiple goroutines discover that an AWS access token or another shared credential needs refreshing.

Without coordination, they may all trigger refresh requests.

**Solution:**

Use the account or credential identity as the singleflight key.

Only one refresh executes per key at a time.

### Use case 4: Customer configuration loading

**Problem:**

Multiple requests need the same customer configuration from an external configuration service.

**Solution:**

Use Customer ID as the key and share the result of one concurrent fetch.

### Use case 5: Expensive database queries

**Problem:**

Multiple API requests trigger the same expensive aggregation query.

**Solution:**

Use a query identity or normalized query key to deduplicate overlapping execution.

Only do this when the query is safe to share and its result is identical for all callers.

## 7. Singleflight vs Other Concurrency Mechanisms

| Mechanism | Problem solved | Example |
|---|---|---|
| Goroutines | Concurrent execution | Concurrent RPC handlers |
| Mutex | Protect shared mutable state | Protect a Go map |
| WaitGroup | Wait for goroutines | Wait for 100 client calls |
| Semaphore | Limit concurrent operations | Maximum 20 DB queries |
| Rate limiter | Limit operations per time interval | 100 requests/second |
| Singleflight | Deduplicate in-flight operations | One lookup per cluster ID |
| Distributed lock | Coordinate across processes | One scheduled job across pods |
| Cache | Reuse previously computed results | Store cluster metadata |

### Singleflight vs Semaphore

These two are particularly important.

**Singleflight:**

```text
100 requests for cluster-101
         |
         v
1 downstream lookup
```

**Semaphore:**

```text
100 requests for 100 different clusters
         |
         v
Maximum 10 concurrent downstream lookups
```

Singleflight controls duplicate work.

Semaphore controls concurrency.

They can also be combined.

## 8. Important Production Limitations

### 8.1 Process-local coordination

Singleflight works only within the same Go process.

Suppose the service runs on five Kubernetes pods.

```text
             Load Balancer
                   |
       +-----------+-----------+
       |           |           |
      Pod-1       Pod-2       Pod-3
       |           |           |
    Group-1     Group-2     Group-3
       |           |           |
    1 lookup    1 lookup    1 lookup
```

If requests for the same key reach all three pods, each pod can execute one lookup.

Singleflight is not a distributed lock.

### 8.2 Context cancellation

With `Do()`, duplicate callers wait for the original execution.

The shared operation is not automatically cancelled when a waiting caller disconnects.

Using `DoChan()` allows an individual caller to stop waiting.

However, the shared operation needs its own cancellation and timeout strategy.

### 8.3 Error sharing

If the leader operation fails, all waiting callers receive the same error.

Singleflight does not automatically retry failed operations.

A subsequent request can try again after the failed call completes.

### 8.4 Result sharing

All callers receive the same result object.

If the result is a pointer to a mutable struct, callers must not independently modify it without synchronization.

Prefer treating shared results as immutable or returning copies.

### 8.5 No persistent caching

After the operation finishes, the in-flight entry is removed.

A new request arriving later executes the function again unless a separate cache is used.

## 9. Production Design: Cache + Singleflight + Semaphore

A common production architecture combines all three.

```text
             Incoming Request
                    |
                    v
                Cache Check
                    |
              +-----+-----+
              |           |
            Cache HIT   Cache MISS
              |           |
              v           v
          Return Data  Singleflight
                          |
                    +-----+-----+
                    |           |
                 Existing    New Call
                   Call         |
                    |           v
                  Wait       Semaphore
                                |
                                v
                         Downstream API
                                |
                                v
                           Update Cache
                                |
                                v
                           Return Data
```

Responsibilities:

1. Cache avoids repeated work across time.
2. Singleflight avoids duplicate work happening simultaneously.
3. Semaphore limits the maximum number of different concurrent operations.

This combination is useful for high-traffic backend services.

---

## 10. Key Takeaways

- Go HTTP and gRPC servers can handle multiple concurrent requests through goroutines.
- Singleflight does not reduce incoming requests or handler goroutines.
- It reduces duplicate downstream operations for the same key.
- Different keys execute independently.
- It is process-local, not cluster-wide.
- It does not replace caching, rate limiting or distributed locking.
- Cache + Singleflight is a common approach to preventing cache stampedes.

**One-line definition:**

Singleflight is an in-flight request deduplication mechanism that ensures only one execution of an expensive operation per key at a time within a Go process, while allowing concurrent callers to share its result.
